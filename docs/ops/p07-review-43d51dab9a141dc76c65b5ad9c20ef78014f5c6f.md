### P2 — Cloud section navigation destroys unresolved command recovery

`frontend/src/App.tsx:282` and `:290`.

The two navigation buttons are always available and a ternary renders only the selected page. Both CloudStudentsPage and CloudDayVendorsPage keep pending command ID, frozen input, unknown/receipt phase and authorization latch in component-local state/refs. Switching sections while submission is pending or UNKNOWN_RESULT is unresolved unmounts the owner. Returning creates an initial page, loses the original command ID/input and permits a new command, so the operator cannot perform the required same-ID receipt confirmation or recovery. Ignoring an old promise after unmount does not recover an already committed server command.

Keep the recovery owner alive across section changes (for example stable page instances with the inactive page hidden, optionally mounting on first visit), or synchronously prevent section changes while a command is unresolved. Scope/UID/epoch changes must still invalidate old async work and clear sensitive data. Regression should cover pending and unknown navigation, retained UUID/frozen semantics and absence of extra UUID generation. The separate navigation owner has been notified; the integrator remains sole committer.
