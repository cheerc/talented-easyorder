## Closed findings

### Navigation no longer destroys an unresolved command's recovery owner

App retains conditional page mounting but both navigation handlers check a synchronous ref gate, in addition to disabled buttons. Each Cloud page reports recovering synchronously at command entry, before awaiting repository work or relying on a React effect. Pending, checking, UNKNOWN_RESULT and confirmed-receipt refresh failure retain recovery state and therefore keep navigation blocked. Once a validated receipt is followed by successful snapshot refresh, recovery clears and the derived callback permits navigation; a definite command rejection can also clear ordinary recovery.

Authorization denial reports revoked synchronously, even if no command ID exists. App retains a sticky revoked bit for that UID:leaseEpoch and will not clear it on a later resolved callback from the same scope. Both pages use the same public identityKey passed by App; P07's additional internal scope suffix is not incorrectly used as the parent key. Existing generation/list/flight invalidation guards still prevent old identity results from publishing or reporting a late authorization state. A different UID or lease epoch establishes a new scope rather than reviving the old page's data.

Committed tests cover parent section blocking/release, same-scope revocation resisting resolved, independent UID-only and epoch-only scope changes, each page's UNKNOWN same-ID/frozen-input recovery, no-ID initial authorization denial, and recovery remaining locked after confirmed-receipt refresh failure. The r11 full Vitest JSON records App.mode 3 passed, CloudStudentsPage 13 passed and CloudDayVendorsPage 18 passed, total 34 passed. This closes the navigation-unmount P2 at the fixed commit.
