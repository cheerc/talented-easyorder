## 實作順序

1. 讀 root/frontend 指引、current handoff、契約 §15、現有 day-close recovery／navigation lock 的測試，核對 base 與乾淨工作區。從指定 base 開 `codex/p11c4b-post-close-ui`。
2. 先補有效 RED：closed 日有新增表單與歷史列表、重開日不可新增、差額入口帶方向金額但不帶原因、unknown 結果沿同 ID recovery、失權資料清除。測試要經元件實際事件，不只測 helper。
3. 在既有 DaySnapshot 與 prepared command/recovery 增加補記路徑，使用 `recordPostCloseEntry`。傳入既有 expectedDayRevision／expectedSettlementRevision，成功後 read(dayId) 並 reload ledger。
4. closed 日展示有效關帳現金與每筆方向、金額、原因、createdBy／createdAt；舊版補記顯示不再計入。reopened 日仍可查舊歷史，表單不顯示。使用台北時間。
5. 異常頁在 gapDayCount==0 時提供補記差額入口，target previousClosedDayId，difference>0 是 income、<0 是 expense；reason 空白。保留「回填」與「關帳後補記」不同標籤。
6. 降低舊差額草稿誤送：導航帶入原異常識別及差額預覽；真正送出前重讀日結與 ledger，核對仍是 closed、同版次、相同差額與對齊開帳日。變更時不自動送出，要求操作者用更新數字再次確認。額度外差額顯示限制，不拆單。送前重讀不是跨分頁鎖：不同 command IDs 仍可能各成功，兩分頁同時重讀後提交及人工補記交錯是既有限制，須在 UI 說明與 PR limitations 揭露，不宣稱 exactly-once、不新增 deterministic ID／backend 鎖。
7. 補 Q2 E2E：合成日關帳1000 → 後日開帳950且無 gap day → 從異常入口帶50支出 → 原因必填 → 提交 → 異常消失、有效現金950、原 settlement countedCash仍1000；重開再關帳後舊補記歷史標記正確。
8. 移除「補記未開放／修正只能重開」等與 R6/R7 矛盾文字，但保留既有合法重開機制及其理由 gate。一般修帳導向補記，學生訂餐／繳費不可經補記修改。
